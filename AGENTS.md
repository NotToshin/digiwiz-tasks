# Working on Digiwiz Tasks

- Read the README, product requirements, workflow, attendance, design, architecture, roadmap and acceptance criteria before making changes for an active phase.
- Pair-program with Toshin. Explain the goal briefly, give Toshin one bounded implementation exercise, and then review it or continue the integration as requested. Keep the app runnable between phases.
- Use React, TypeScript, Vite, Node.js, Express, and Hostinger-compatible MySQL. Use TypeScript on both sides.
- Preserve task history, attendance corrections, and permissions across changes. Enforce the office network rule and permissions on the server. Treat attendance and work timers as separate records.
- Use fictional sample data and a local email test inbox during development. Never commit credentials or personal staff data. Never ship development network bypasses.
- If a user correction changes a rule, update the relevant document and acceptance criteria in the same phase. Ask about open policy choices before using real staff data or changing hosting resources.
- End each phase with verified checks, the commands to run, and a short walkthrough of what Toshin can inspect.
